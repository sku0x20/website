For four years, the backend was stuck in a split state: partly Java, partly Kotlin.

When I inherited the codebase, it was roughly 60% Kotlin and 40% Java. Over time, I chipped away at it during feature work, gradually pushing it to around 72%.

And then it stalled.

Mechanical refactoring is pure friction. Nobody gets two uninterrupted weeks to sit down and translate hundreds of files by hand, and running automated converters creates more problems than it solves. So the remaining 28% sat there for years.

Last week, I finished the rest of it in two or three days using Claude Code.

---

## Why I Still Prefer Kotlin

Modern Java is trying hard. Java 21 brought records, pattern matching, virtual threads. 

Yet every time I write modern Java, it feels caught in an identity crisis. It is not purely object-oriented anymore, but it is certainly not functional. It sits awkwardly in the middle—ceremonial, noisy, and far too verbose.

Kotlin just gets out of the way. DTOs collapse from 200 lines of boilerplate into single data classes, property access has no Lombok trickery, and call-site generics don't require wrestling wildcards. When I read code, I want domain logic, not syntax ceremony.

I don't love everything about it—replacing standard bitwise operators (`<<`, `>>`, `&`, `|`) with infix words (`shl`, `shr`, `and`, `or`) still annoys me every time I see it. But day to day, Kotlin is clean, expressive, and pleasant to maintain.

## The Auto-Convert Trap

Early on, I tried the obvious route: IntelliJ's built-in converter (`Cmd+Alt+Shift+K`).

It looks like magic for thirty seconds. Then you look at the diff.

Before me, someone had run the auto-converter across large swaths of the codebase and committed the result without checking. I spent years paying off that carelessness.

### The Nullable Var Explosion
IntelliJ is overly conservative. Instead of reading intent or using `lateinit var`, it takes the path of least resistance:

```kotlin
// What auto-convert produced
var customerName: String? = null
var orderItems: List<Item>? = null
```

Suddenly, non-nullable Java fields became mutable, nullable Kotlin variables. Safe calls (`?.`) and double-bangs (`!!`) spread across callers like an infection.

### The Jackson & Mongo Collision

The underlying issue was identical—Jackson applying JavaBean property heuristics to Kotlin's generated bytecode accessors—but it manifested as two completely different kinds of bugs: one silently corrupted database documents, while the other threatened API wire contracts.

#### 1. The `is...` Getter Stripping Bug (Database Corruption)

In Kotlin, if you have a boolean property starting with `is`:

```kotlin
var isOffline: Boolean = false
```

The Kotlin compiler generates a getter named `isOffline()` and a setter named `setOffline()`.

Jackson inspects that getter, follows JavaBean conventions, and trims the `is` prefix—deciding the JSON key is `"offline"`. 

Meanwhile, the MongoDB driver inspects the class differently. Between Jackson trimming prefixes and Mongo trying to match fields and accessors, the database driver ends up writing wrong or phantom duplicate fields into the database—persisting both `isOffline` and `offline` in the exact same document.

I had run into this exact ghost in the past during hand-migrations, and back then it took hours to isolate why documents were suddenly sprouting dual boolean fields. 

The fix is telling Jackson to leave the prefix alone by pinning `@get:JsonProperty` directly on the getter:

```kotlin
@get:JsonProperty("isOffline")
var isOffline: Boolean = false
```

#### 2. The `stale` vs `isStale` Wire Mismatch (API Contract Divergence)

The flip side happens when the database schema and the API contract disagree on naming.

Say you have a boolean field stored in MongoDB as `stale`, but the frontend and external clients expect `isStale` over the wire.

Some people "fix" this by renaming the field in code to `isStale` and slapping Spring Data's `@Field("stale")` on it to remap it for MongoWriter. I refuse to do that. My rule is that the Kotlin entity model must match the database schema 1:1—no `@Field` scaffolding or persistence-layer gymnastics just to satisfy a JSON serializer. 

If the database has `stale`, the entity field stays `stale`. You fix the wire contract at the serialization boundary:

```kotlin
@get:JsonProperty("isStale")
var stale: Boolean = false
```

What makes this work cleanly in both directions is how Jackson's property introspection works under the hood:

1. **Implicit grouping**: The Kotlin compiler generates `getStale()` and `setStale(...)`. Because both share the same implicit name (`stale`), Jackson merges them into a single logical property before it even looks at annotations.
2. **Unified rename**: Jackson then applies the `@get:JsonProperty("isStale")` rename to that *whole merged property*, not just the getter it sits on.

In one line, you get the exact wire contract you want for both serialization (via getter) and deserialization (via setter)—while the entity remains a pristine 1:1 mirror of the database document without a single `@Field` annotation.

---

Because I already bore those scars, this time it wasn't a multi-hour debugging rabbit hole. Across the 10–11 files where boolean flags lived, I caught them in the diffs, added `@get:JsonProperty`, and kept moving.

## Claude Code as an Adaptive Macro

When I picked up Claude Code CLI for this pass, I didn't write an elaborate prompt. 

I didn't need to.

The codebase was already 72% Kotlin. The patterns were already there.

At its core, this migration wasn't creative programming. It was **contextual pattern matching**:
- No behavioral changes.
- No architectural rewrites.
- Take class X in Java, translate it into Kotlin, and match the exact idioms already present in the rest of the project.

A human can do that easily, but going class by class, fixing callers, untangling properties, and adjusting annotations drains your willpower. Traditional IDE macros can't do it because they don't understand cross-file semantic context.

Claude Code acted as an adaptive macro: reading the existing Kotlin conventions in the codebase, applying them cleanly to the Java classes, and fixing callers across files.

---

## The Discipline: One File, One Commit

To keep from drowning in massive diffs or hidden breakages, I enforced a strict mechanical loop: migrate one class, fix affected callers, compile-check, and commit individually.

Every migration got its own atomic commit: the converted class plus all callers affected by the new Kotlin types. If Claude went down a dead end—like trying to rewrite a deprecated external wrapper that was better left alone in Java—reverting was a one-liner: tell Claude to revert the last commit. Clean, done, no unpicking git history.

Running the full integration test suite after every single file was too slow, but waiting fifty files was asking for a debugging nightmare. Five commits was the sweet spot: five clean compiles, run the integration test suite, and if green, push to remote. Fast rhythm, zero anxiety.

## The Final Five

Out of ~200 files, the vast majority fell into place with minimal fuss—isolated utilities, DTOs, straightforward services. 

The last five files took almost as much time as the rest combined.

In a clean architecture, they shouldn't have. But as I wrote about in [Double-Encoded Strings and the Normalization of Stupidity](/blog/double-encoded-strings-and-the-normalization-of-stupidity), this backend was built on years of spaghetti: 10,000-line controllers and God classes knowing about everything from raw database connections down to string escaping.

These final five were the nexus points: the most interconnected, heavily joined classes in the entire backend. Converting one didn't just mean fixing two or three callers; it meant dealing with tentacles reaching into dozens of files. Every change cascaded, unearthing circular dependencies, hidden side effects, and subtle type mismatches that required careful untangling before the compiler would pass.

---

## The Two-Way Learning Loop

The unexpected part of this pass was how much I learned.

When Claude did something suboptimal, I spotted it immediately and corrected it. But just as often, it structured a translation differently than I would have. I'd pause, look at the diff, and realize it was much cleaner than my initial instinct.

Seeing idiomatic semantics applied directly to my own domain models—rather than textbook examples—made the patterns stick. I picked up standard library functions I forgot existed, cleaner property delegation, and tighter type expressions.

It wasn't just code moving from Java to Kotlin. My own mental model of Kotlin grew along with it.

---

In two or three days, the remaining 28% of Java was gone. 100% Kotlin, zero regressions, and none of the nullable-var scars from old auto-conversions.

Four years of a split codebase, settled in a few afternoons. 

No drama. Just a tight loop, atomic commits, and a tool that finally knows how to match patterns without making a mess.
